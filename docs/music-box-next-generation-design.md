# 新音乐盒完整实现方案

> 状态：设计方案，尚未实现。
>
> 当前已上线接口与行为仍以 [`music-box-api.md`](music-box-api.md) 为准。本文档描述下一代音乐盒的目标架构、完整运行流程、兼容迁移顺序和验收标准，供后续客户端与服务端开发共同使用。

> 产品界面统一将领域模型中的“临时歌单”显示为“点歌队列”。为兼容已发布客户端、服务端和数据库，协议枚举 `temporary`、JSON 字段 `temporary_playlist` / `temporary_queue` 及代码内部类型名称保持不变。

## 1. 目标

在保留现有“服务端音乐机器人向 LiveKit 房间广播单条 Opus 音轨”方案的基础上，安全地增加：

- 上一首、下一首。
- 顺序播放、单曲循环、列表循环、随机播放。
- 每个房间默认拥有一个初始为空的临时歌单，房间成员的直接点歌统一加入该临时歌单。
- 点歌队列行显示音乐图标与来源；歌曲名片显示可信点歌人，并由服务端限制删除、清空和优先播放权限。
- 在临时歌单、已保存的房间歌单和个人歌单之间安全切换。
- 可持久保存、编辑和复用的歌单。
- 跨房间复用的音频缓存。
- 控制命令的确定性确认和跨客户端一致状态。
- 服务重启后保留歌单和播放队列，但不擅自恢复声音。
- 能够支撑较长歌单而不逐秒推送完整列表。

本方案不把房间音乐的下载和播放权威迁移到 Windows、macOS 或 Android 客户端。三个客户端继续只负责搜索、控制、展示和接收 LiveKit 音频，所有房间播放规则由服务端统一执行。唯一例外是用户在个人/房间歌单管理页明确触发的本地“试听”：它使用独立缓存和本地播放器，不加入房间队列、不广播、不修改 revision，并在歌曲名片关闭或取消试听时立即停止。

## 2. 非目标

第一阶段不实现：

- 客户端离线播放或下载歌曲。
- 用户上传本地歌曲文件。
- 跨房间同步播放同一个歌单进度。
- 歌词逐字同步。
- 播放器均衡器或服务端房间总音量。
- 自动恢复服务重启前的播放位置并立即出声。
- 永久保存所有播放过的音频文件。

临时歌单不是可复用的收藏歌单：它不支持随机播放或列表循环，也不能被其他房间引用。临时歌单默认顺序播放，并允许临时切换为单曲循环。已保存的房间歌单和个人歌单支持本文定义的全部播放模式。

## 3. 必须保留的现有架构

当前播放链路是：

```text
客户端搜索/点歌
  -> Gang Chat 服务端解析音源
  -> FFmpeg 转码为 48 kHz 双声道 Ogg/Opus
  -> 房间专属 __musicbox__ LiveKit 参与者
  -> 所有已加入语音频道的客户端接收同一条远端音轨
```

这条链路应继续保留，原因包括：

- 房间成员天然听到同一首歌和同一播放进度。
- 音源地址、下载鉴权和转码能力不需要暴露给客户端。
- Windows、macOS、Android 不需要分别维护本地播放器。
- 当前播放器会直接读取 Ogg 中的 Opus packet 并写入 LiveKit，不在播放过程中重复解码、编码。
- 本地听歌音量仍可以由每个客户端单独控制，不改变房间播放状态。

不应改为“服务端只广播播放指令、每个客户端自行拉取歌曲”。这种方案会重新引入音源兼容、重复流量、客户端时钟漂移、后台播放限制和不同设备解码差异。

## 4. 当前实现需要解决的问题

### 4.1 播放完成会消费并删除队列项

当前歌曲自然结束或跳过后，队列记录及其 Ogg 文件都会被删除。该行为不支持上一首、列表循环、随机历史和缓存复用。

新实现必须把以下概念拆开：

- 歌曲元数据。
- 可持久保存的歌单。
- 房间默认的临时歌单与当前激活歌单。
- 从已保存歌单生成的房间本轮播放快照。
- 播放历史。
- 可随时清理、重新生成的音频缓存。

### 4.2 控制命令可能返回旧状态或被丢弃

当前播放器控制 channel 使用非阻塞写入，队列满时命令会被静默忽略；HTTP handler 在播放器实际处理命令前就可能返回快照。

新实现要求：

- 每条控制命令都有唯一 `command_id`。
- 房间播放状态机按顺序处理命令。
- HTTP 响应必须等待命令应用成功、明确失败或超时。
- 成功响应包含应用后的 `revision` 和权威快照。
- channel 满、播放器关闭、请求超时都必须返回明确错误，不能静默吞掉。

### 4.3 快照可能乱序覆盖

当前客户端会用 HTTP 响应或 SSE 快照整体覆盖本地状态，但快照没有版本号。旧 HTTP 响应或旧 SSE 事件晚到时可能覆盖新状态。

新状态必须带单调递增的 `revision`。客户端仅接受：

- `revision` 大于当前值的完整快照。
- `revision` 等于当前值且 `current_item_id` 匹配的进度事件。
- 旧服务端未提供 `revision` 时，继续使用现有兼容行为。

### 4.4 每秒写数据库并发送完整队列

当前播放心跳每秒保存状态并广播包含完整队列的快照。短队列影响有限，但大型歌单会放大数据库写入和 SSE 流量。

新实现应区分结构事件和进度事件：

- 队列、当前歌曲、播放模式或播放状态变化时发送完整快照。
- 正常播放进度只发送精简进度事件。
- 数据库只在重要状态边界和周期检查点保存，不必每秒写入。

### 4.5 当前排序分配和删除边界不足

队列排序不能继续使用未加事务保护的 `MAX(sort_order) + 固定步长`。并发点歌必须通过事务或房间状态机分配唯一顺序。

所有查询、修改和删除必须同时限定 `room_id` 与 `item_id`，不能只凭全局 item ID 操作记录。

### 4.6 当前文档和代码存在进度同步历史差异

现有部分注释仍描述“客户端本地推进进度”，现行实现则依赖服务端每秒快照。实施新方案时应同时更新现有 API 文档、协议模型注释和测试，避免两套契约并存。

## 5. 目标模块结构

### 5.1 服务端

建议在 `gang-chat-server/internal/musicbox` 内逐步形成以下职责：

```text
manager.go           对外入口、房间引擎生命周期
engine.go            单房间串行播放状态机
selector.go          上一首/下一首/播放模式的纯规则
player.go            LiveKit 连接和 Opus packet 播放
playlist_store.go    歌单和歌单项持久化
queue_store.go       房间临时歌单、活动播放快照和播放历史持久化
state_store.go       房间播放状态、revision 和恢复点
cache.go             音频缓存索引、租约、LRU 清理
prepare.go           音源解析、下载、转码和预取调度
transcode.go         FFmpeg 适配器
types.go             领域类型和枚举
```

不要求一次性按文件名重写现有实现，但最终职责必须清晰，不能继续让一个队列行同时承担歌曲、历史和缓存文件的生命周期。

### 5.2 客户端

遵守 `modular-development-guide.md` 的依赖边界：

- `lib/src/protocol`
  - 扩展 API、SSE 事件和数据模型。
  - 兼容缺失字段和未知播放模式。
- `lib/src/app`
  - 扩展 `MusicBoxController`。
  - 增加播放模式、控制按钮状态、revision 接收规则等纯逻辑。
  - 不依赖 Flutter、LiveKit 或平台插件。
- `lib/src/home`
  - 渲染上一首、播放/暂停、下一首和模式按钮。
  - 展示歌单、队列、加载、失败和空状态。
  - 只调用 controller，不拼 API body。
- `lib/src/live`
  - 继续只负责识别音乐机器人音轨和设置本地监听音量。
  - 不承担播放顺序、歌单或随机规则。
- `lib/src/ui`
  - 只在确有跨页面复用需求时增加通用歌单/菜单组件。

三端共享同一套协议和业务规则。平台差异只允许出现在响应式布局、输入方式和本地音频输出适配中。

## 6. 领域模型

### 6.1 Track：歌曲元数据

建议建立规范化歌曲表，使用 `(source, external_track_id)` 作为业务唯一键。

主要字段：

- `id`
- `source`
- `external_track_id`
- `title`
- `artist`
- `duration_ms`
- `cover_ref`
- `metadata_version`
- `created_at`
- `updated_at`

客户端提供的歌名、歌手只能作为搜索结果展示和入队初值。服务端在解析音源时应校验并尽量回填权威元数据，同时限制字符串长度。

### 6.2 Playlist：持久歌单

主要字段：

- `id`
- `scope_type`：`user` 或 `room`
- `owner_user_id`：个人歌单必填，房间歌单为空
- `room_id`：房间歌单必填，个人歌单为空
- `name`
- `description`
- `revision`
- `created_at`
- `updated_at`

### 6.3 PlaylistItem：歌单条目

主要字段：

- `id`
- `playlist_id`
- `track_id`
- `sort_order`
- `added_by_user_id`
- `created_at`

重复歌曲允许存在，并计入歌单上限。排序更新必须在事务中完成，并对 `(playlist_id, sort_order)` 建立约束或使用可安全重排的顺序方案。

### 6.4 RoomQueueItem：房间活动播放条目

临时歌单是房间默认的工作队列；已保存歌单是长期模板。无论当前来源是哪一种，播放器都通过房间活动播放条目工作。切换到已保存歌单时，服务端创建独立播放快照，后续编辑原歌单不会在播放中途改变当前顺序。

主要字段：

- `id`
- `room_id`
- `track_id`
- `queue_scope`：`temporary` 或 `saved_playlist_snapshot`
- `source_playlist_id`：直接点歌时为空
- `source_playlist_item_id`：直接点歌时为空
- `requested_by_user_id`
- `requested_by_snapshot`：可选的点歌时昵称/头像摘要，仅用于历史展示降级，权限判断始终使用用户 ID
- `sort_order`
- `lifecycle`：`queued`、`playing`、`played`、`interrupted`、`skipped`、`removed`、`failed`
- `played_sequence`
- `created_at`
- `updated_at`

播放结束后不立即物理删除队列项，而是标记为 `played` 或 `skipped`。这部分记录用于上一首、播放历史和随机模式回退。临时歌单的已播放记录只保留一个有上限的历史窗口；已保存歌单快照可以按模式重新选择原条目。房间主动清空临时歌单、切换快照或历史过期时再批量删除对应记录。

### 6.5 RoomPlaybackState：房间播放状态

建议在现有状态表上增加：

- `mode`：`sequential`、`repeat_one`、`repeat_all`、`shuffle`
- `active_source_type`：`temporary`、`room_playlist`、`user_playlist`
- `active_playlist_id`：临时歌单为空
- `active_snapshot_revision`：已保存歌单载入时的 revision
- `active_playlist_owner_user_id`：个人歌单填写，临时歌单和房间歌单为空
- `active_playlist_owner_room_role`：个人歌单载入或权限刷新时的服务端角色摘要，仅供展示与快速判断，授权时必须读取当前权威角色
- `revision`
- `current_queue_item_id`
- `position_ms`
- `state`：继续兼容 `stopped`、`playing`、`paused`
- `shuffle_cycle`
- `shuffle_seed` 或当前洗牌序列标识
- `voice_empty_since`
- `temporary_playlist_generation`：用于拒绝迟到的自动清理事件
- `updated_at`

播放过程中内存状态机是实时权威来源，数据库是恢复点。数据库写入失败不能阻塞 20 ms 的音频写入路径，但必须被记录并重试或降级。

### 6.6 房间临时歌单

每个房间首次启用音乐盒时创建一个逻辑上的临时歌单，初始内容为空。它遵守以下规则：

- 房间内每个有点歌权限的成员直接点歌时，歌曲都加入该房间的临时歌单。
- 每个临时歌单条目必须保存 `requested_by_user_id`，并在快照中返回可展示的点歌人信息。
- 临时歌单属于房间，不属于某个用户，也不能跨房间复用。
- 临时歌单不出现在“已保存歌单”列表中，不支持重命名、分享、随机播放或列表循环。
- 默认模式为 `sequential`，唯一可切换的其他模式为 `repeat_one`。
- 切换到已保存歌单时不清空临时歌单；切回临时歌单后继续使用其剩余队列和受限播放历史。
- 临时歌单可以作为房间恢复点持久化，但不因此变成可复用歌单。首次创建、用户明确清空或按产品保留策略过期后均为空。
- 普通成员在临时歌单中只能点歌、切换到有权访问的歌单，以及删除自己点的临时条目；不能执行其他播放或队列管理操作。
- 房间管理员及更高权限可以删除任意临时条目、一键清空临时歌单，以及让某个临时条目立即播放。
- 语音频道连续无人达到服务端配置的宽限时间后，自动清空临时歌单和本轮活动快照，但绝不删除已保存的房间歌单或个人歌单。

为了支持上一首，临时歌单应保存最近一部分真实播放历史，建议默认 20 首并允许服务端配置。超过上限时按播放先后淘汰最旧记录；正在播放的条目和仍在待播队列中的条目不受历史淘汰影响。

### 6.7 当前激活歌单

每个房间同一时间只有一个激活来源：

- `temporary`：房间默认临时歌单。
- `room_playlist`：已保存的房间歌单。
- `user_playlist`：当前操作者有权访问的个人歌单。

切换到已保存歌单时，服务端按该歌单的当前 revision 创建活动快照，不直接在原歌单上记录播放状态。切换回来不会修改或删除临时歌单。成员在任何激活来源下直接点歌，歌曲都只加入临时歌单；如果当前播放的是已保存歌单，客户端应显示临时歌单新增数量，但不得静默修改或切换当前已保存歌单。

切换到某个歌单不等于获得该歌单的控制权。服务端根据当前操作者、歌单作用域、歌单所有者和双方在房间内的有效角色，为每个快照动态计算 capabilities：

- 普通成员对自己的个人歌单拥有完整播放控制、条目重排和播放模式切换。
- 普通成员对房间歌单拥有完整播放控制、条目重排和播放模式切换。
- 普通成员可以切换到有权访问的其他成员个人歌单，但不能控制播放、重排条目或切换模式。
- 房间管理员及更高权限，对房间内权限严格低于自己的用户所拥有的个人歌单，拥有上述全部控制权限。
- 管理员不能借此控制与自己同级或权限更高用户的个人歌单。

这里的“控制权限”不自动转移歌单所有权。删除整个个人歌单、修改其名称/简介、改变共享范围等所有权操作仍遵守个人歌单归属规则；是否允许管理员增删低权限用户个人歌单中的持久条目，应作为独立权限明确配置，不能从播放控制权限推导。

### 6.8 MediaCache：服务端音频缓存

音频文件不属于客户端、不属于歌单，也不属于某个队列项。它是服务端可重建缓存。

缓存键建议为：

```text
source + external_track_id + encoding_profile_version
```

例如：

```text
netease:108485:opus-48k-stereo-fec-v1
```

缓存索引字段包括：

- `cache_key`
- `track_id`
- `encoding_profile`
- `status`：`missing`、`preparing`、`ready`、`failed`
- `file_path`
- `file_size_bytes`
- `duration_ms`
- `checksum`
- `last_accessed_at`
- `failure_count`
- `retry_after`

正在播放或已被预取任务占用的缓存必须持有租约，清理器不能删除。进程崩溃后租约应能过期，不能依赖永久引用计数。

## 7. 存储位置与容量限制

### 7.1 保存位置

- 歌单、歌曲元数据、播放队列、历史和状态：服务端数据库。
- Ogg/Opus 音频：服务端本地磁盘缓存。
- 客户端：除用户明确触发且可随时重建的试听缓存外，不保存完整歌曲；其余只保存 UI 状态、封面缓存和本地音量偏好。
- 对象存储：第一版不要求；多服务实例部署时可以作为可选共享冷缓存。

音频缓存被清理后，歌单仍然完整。再次播放时服务端重新解析、下载和转码。

### 7.2 默认限制

限制必须由服务端配置和响应能力字段提供，客户端不能硬编码为唯一真值。

建议默认值：

| 项目 | 建议上限 |
|---|---:|
| 单个个人歌单 | 500 首 |
| 单个账号歌单数量 | 50 个 |
| 单个房间歌单 | 500 首 |
| 单个房间保存歌单数量 | 50 个 |
| 房间活动播放队列 | 200 首 |
| 房间临时歌单播放历史 | 20 首 |
| 空语音频道临时歌单保留时间 | 建议 10 分钟，可配置 |
| 迁移期间旧完整快照队列 | 暂时 100 首 |
| 歌单/队列分页大小 | 50 首 |
| 搜索默认返回数量 | 20 首 |
| 预取范围 | 当前歌曲之后 2 首 |

大型歌单只加载元数据，不一次性下载全部歌曲。达到上限时服务端返回稳定错误码，客户端提前显示剩余容量。

## 8. 单房间播放状态机

### 8.1 单一写入者

每个活动房间创建一个 `RoomPlaybackEngine`。该引擎是房间播放状态的唯一写入者，依次处理：

- `enqueue`
- `enqueue_playlist`
- `switch_playlist`
- `play_now`
- `remove_item`
- `clear_temporary_playlist`
- `play`
- `pause`
- `resume`
- `previous`
- `next`

数据库事务、播放选择和 revision 增长由引擎统一协调。下载、转码和 LiveKit I/O 可以在后台执行，但完成结果必须作为事件重新投递给引擎，不能从后台 goroutine 直接修改房间状态。

### 8.2 命令确认

每个控制命令包含：

- `command_id`
- `room_id`
- `actor_user_id`
- `action`
- 可选 `expected_revision`
- 超时上下文

状态机处理后返回：

- 是否应用成功。
- 新 `revision`。
- 应用后的完整状态或明确错误。

不允许使用 `default` 分支静默丢弃控制命令。高频重复命令可以按 `command_id` 做幂等去重。

### 8.3 基础状态转换

| 当前状态 | 事件 | 结果 |
|---|---|---|
| stopped | play | 准备并播放当前项；无当前项时选择第一项 |
| playing | pause | 保留当前项和位置，停止发送 packet |
| paused | resume/play | 从当前位置继续 |
| playing/paused | next | 按模式选择下一项，保持原先播放/暂停状态 |
| playing/paused | previous | 按上一首规则选择，保持原先播放/暂停状态 |
| playing | track_ended | 按模式选择下一项并继续播放 |
| 任意 | stop | 停止出声，位置归零，保留队列 |
| 任意 | set_mode | 更新模式，不立即切歌 |
| 任意 | switch_playlist | 保存当前来源上下文，载入目标来源快照并切换 |
| playing/paused | play_now | 立即切到指定条目；当前来源是点歌队列时先把目标移到刚才播放歌曲的下一位，其他歌单保持原顺序 |
| 任意 | temporary_playlist_expired | 停止临时播放并清空临时待播项与历史；丢弃活动快照 |

如果当前项还没有缓存，状态保持可解释的“正在准备”展示，但协议的基础 `state` 仍兼容现有枚举。可以额外增加 `phase` 字段表示 `idle`、`preparing`、`streaming`、`reconnecting` 或 `failed`。

`play_now` 必须是一个原子的状态机命令：

1. 校验操作者至少为房间管理员，且目标条目属于当前活动队列。
2. 取消当前音频文件读取和目标歌曲的低优先级预取，但复用现有 LiveKit 音乐机器人
   连接与已经发布的 Opus track；优先切歌不能通过断开旧机器人、轮询清理、再使用同一
   identity 重连来实现。
3. 当前正在播放的条目以 `interrupted` 原因压入真实播放历史，成为紧邻目标歌曲的上一首；当前来源是已保存歌单时，历史项同时保存原来源信息。
4. 当前来源是点歌队列时，把目标条目原子移动到被中断歌曲的下一位；当前来源是房间歌单或个人歌单时保持活动快照顺序不变。
5. 把目标条目提升为当前项，不复制条目、不改变点歌人。
6. 目标未准备好时进入可见的 `preparing`，准备完成后强制进入 `playing`，不继承原来的暂停状态。
7. revision 只增长一次，并向所有客户端广播应用后的权威快照；HTTP 命令只能在目标
   已成为当前歌曲、位置归零且播放状态确定后确认成功。

如果当前没有歌曲，`play_now` 直接选择目标；如果目标就是当前歌曲，则从头开始并进入 `playing`，不重复写入历史。
如果当前没有播放器，应先成功建立 LiveKit 连接，再提交目标当前项；建连失败不得留下
目标已写入但实际上没有播放器的半成功状态。

## 9. 播放模式规则

可用模式由当前激活来源决定，服务端必须校验，客户端只负责提前禁用不适用选项：

| 激活来源 | 顺序播放 | 单曲循环 | 列表循环 | 随机播放 |
|---|---:|---:|---:|---:|
| 房间临时歌单 | 支持，且为默认 | 支持 | 不支持 | 不支持 |
| 已保存房间歌单 | 支持 | 支持 | 支持 | 支持 |
| 已保存个人歌单 | 支持 | 支持 | 支持 | 支持 |

切换激活来源后，如果原模式不被新来源支持，则服务端必须原子回退到 `sequential`，并在同一个新 revision 的完整快照中返回实际模式。

### 9.1 顺序播放 `sequential`

- 按队列的稳定顺序播放。
- 到最后一首后进入 `stopped`。
- 不因为后面的歌曲先下载完成而越过尚在准备的队首歌曲。
- 当前歌曲明确失败或准备超时后，标记失败并前进到下一首。

### 9.2 单曲循环 `repeat_one`

- 当前歌曲自然播放结束后从头重复当前歌曲。
- 手动 `next` 仍前进到下一首，不能被单曲循环拦截。
- 手动 `previous` 仍遵守播放进度和真实历史规则。
- 当前歌曲失败、被移除或不可再用时选择下一首，不能无限重试故障歌曲。
- 临时歌单和已保存歌单都允许使用该模式。

### 9.3 列表循环 `repeat_all`

- 到最后一首后回到第一首可播放歌曲。
- 手动 `next` 正常前进。
- 手动 `previous` 按历史回退。
- 单曲队列会持续重复这一首。

### 9.4 随机播放 `shuffle`

使用洗牌袋，不在每次切歌时独立随机：

1. 新一轮开始时对所有有效队列项生成一次随机顺序。
2. 一轮内每首最多播放一次。
3. 一轮结束后生成下一轮顺序。
4. 避免新一轮第一首与上一轮最后一首相同；单曲除外。
5. 新增歌曲加入尚未播放集合，不改动已经播放的历史。
6. 删除歌曲时同时从尚未播放集合移除。
7. `previous` 读取真实播放历史，不重新随机。

洗牌顺序或足以重建它的 seed、cycle 和历史必须持久化，不能在进程重启后产生与已展示状态冲突的新顺序。

## 10. 上一首与下一首

### 10.1 上一首

建议采用常见播放器规则：

- 当前歌曲已播放超过 3 秒：回到当前歌曲开头。
- 当前歌曲不超过 3 秒：返回播放历史中的上一首。
- 没有历史时：回到当前歌曲开头，按钮可以保持可用；完全没有当前项时禁用。
- 随机模式依据历史回退，不能重新随机。
- 临时歌单只需在服务端配置的历史窗口内支持上一首；超过窗口的旧歌曲可以被淘汰。
- 暂停状态下切换后仍保持暂停。

阈值应由服务端常量定义，并通过测试固定，不在客户端重复判断。

### 10.2 下一首

- `next` 和旧接口中的 `skip` 保持等价。
- 手动下一首与自然播放结束都进入同一选择函数，但携带不同原因。
- 单曲循环中只有自然结束重复当前项，手动下一首仍前进。
- 当前项被删除时，使用与手动下一首相同的安全释放和选择流程。

## 11. 完整业务流程

### 11.1 搜索歌曲

1. 客户端输入关键词，延续现有防抖和旧请求失效机制。
2. 服务端校验房间访问权限、音源和分页参数。
3. 服务端查询音源，可对短时间相同搜索做小容量 TTL 缓存。
4. 服务端返回规范化 `source`、`external_track_id`、歌名、歌手、时长和封面引用。
5. 搜索不触发音频下载。

### 11.2 添加到已保存歌单

1. 客户端提交目标歌单和搜索结果的稳定音源 ID。
2. 服务端根据目标类型验证个人歌单归属，或验证房间歌单的管理权限、条目上限和字段长度。
3. 服务端以 `(source, external_track_id)` 获取或创建 Track。
4. 在事务内分配唯一顺序并写入 PlaylistItem。
5. 歌单 revision 加一。
6. 返回更新后的歌单摘要或对应分页。

房间管理员新建房间歌单时可以选择“导入我的歌单”。客户端只提交新歌单名称和当前用户所选个人歌单 ID；服务端必须在同一事务中重新校验个人歌单归属、房间管理权限、房间歌单数量上限与单歌单 500 首上限，然后创建房间歌单并按原顺序复制全部歌曲。导入歌曲获得新的歌单项 ID，任何一步失败都回滚，不能留下空歌单或部分歌曲。未提交导入 ID 的旧客户端继续走原有空歌单创建逻辑。

### 11.2.1 在歌单管理页试听

1. “设置 → 我的歌单”和“房间设置 → 房间歌单”的歌曲行复用歌曲名片；主操作显示“试听”，不能调用房间的 `play_now` 或切换当前歌单。
2. 客户端以稳定的 `source + track_id` 请求经过登录鉴权的试听文件。服务端复用音源解析和 FFmpeg 转码能力，将三个客户端均可原生播放的 M4A/AAC 写入独立、有容量上限的共享试听缓存；并发请求同一歌曲时只准备一次。房间权威播放仍使用 Ogg/Opus，不受试听格式影响。
3. 客户端先查本地应用缓存；未命中时按钮图标显示转圈，下载完成并原子写入缓存后才开始播放，按钮改为“取消试听”。同一页面同时最多试听一首。
4. 关闭歌曲名片、点击“取消试听”、切换到另一首或销毁歌单页面时必须停止并释放播放器；已经返回的旧异步任务不得在名片关闭后重新开始播放。
5. Android 使用不请求音频焦点且不修改系统通话模式/扬声器路由的独立播放器，避免打断 WebRTC 语音；Windows 与 macOS 使用可混音的本地播放器。若平台播放仍失败，只提示试听失败，不改变语音频道状态。

### 11.3 播放歌单

提供两个明确动作：

- `switch_and_play`：把目标已保存歌单设为激活来源，生成活动快照并从头开始播放。
- `switch`：切换激活来源并生成活动快照，但保持停止状态。
- `append_to_temporary`：把已保存歌单内容复制到房间临时歌单末尾，不改变当前激活来源。

完整流程：

1. 校验用户是房间成员且有播放控制权限。
2. 校验歌单可访问。
3. 在一个事务中把歌单项复制为 RoomQueueItem。
4. `switch`/`switch_and_play` 保存临时歌单上下文并更新 `active_source_type`、`active_playlist_id` 和快照 revision；`append_to_temporary` 只修改临时歌单。
5. 服务端根据歌单作用域、所有者和当前房间角色计算操作者 capabilities；对其他成员个人歌单，只有角色严格高于所有者的管理员才能获得控制。
6. 保留来源歌单和来源条目 ID，用于 UI 标识，但后续编辑歌单不自动改变活动快照。
7. 房间 revision 加一。
8. `switch_and_play` 只有在操作者具备播放控制权限时才能开始播放；普通成员切到他人歌单时只能选中和查看。
9. 返回命令应用后的完整快照与 capabilities。

切回临时歌单使用专门的 `switch_playlist` 命令，目标类型为 `temporary`。服务端恢复它的待播条目、当前项和受限历史；如果恢复点无效，则安全回到第一首待播歌曲或空状态。

房间角色或歌单访问权发生变化时，状态机必须提升 revision 并重新发布 capabilities。已经排队但尚未执行的控制命令在真正应用前再次读取当前角色，不能沿用提交时或切换歌单时的旧授权结果。

### 11.4 直接点歌

1. 客户端提交稳定音源 ID 和幂等键。
2. 状态机始终为房间临时歌单串行分配唯一顺序，不因当前正在播放个人歌单或房间歌单而改变目标。
3. 服务端从已认证会话写入 `requested_by_user_id`，不能接受客户端伪造点歌人。
4. Track 已存在时复用；不存在时创建元数据记录。
5. 新队列项进入 `queued`。
6. 如果临时歌单是激活来源且房间没有当前歌曲，立即选为当前项；如果当前激活的是已保存歌单，则保持当前播放不变。
7. 只有临时歌单是激活来源时，才按当前项和后续两首启动预取。
8. 返回新的 revision、完整快照、点歌人和临时歌单待播数量，所有已连接客户端都能看到该成员的点歌结果。

### 11.5 准备音频

1. 根据 Track 和编码 profile 生成 cache key。
2. 缓存命中且文件校验有效：取得租约并立即可播放。
3. 缓存正在准备：加入同一个等待任务，不重复启动 FFmpeg。
4. 缓存缺失：解析临时音源 URL，启动受 worker pool 限制的下载/转码任务。
5. 如果源文件已经是满足要求的 Ogg/Opus，可执行经过验证的快速路径；否则继续完整转码并保留 FEC 参数。
6. 输出先写临时文件，完成校验后原子移动到最终路径。
7. 成功或失败结果作为 `track_ready`/`track_failed` 事件交回房间状态机。
8. 队列项删除或顺序变化时，取消不再需要且无人共享的预取任务。

### 11.6 开始播放

1. 状态机取得当前缓存租约。
2. 确保房间音乐机器人已连接 LiveKit。
3. 打开 Ogg 文件并从头或指定恢复点读取 Opus packet。
4. 写入 LiveKit sample track，并按 packet duration 节流。
5. 更新内存中的 position，不在 20 ms packet 路径执行数据库或 SSE I/O。
6. 播放开始后发布一次完整状态快照。

### 11.7 暂停与恢复

1. 命令进入房间状态机并校验当前 revision。
2. 播放器暂停或恢复 packet 输出。
3. 状态机保存准确 position 和新状态。
4. revision 加一并发布完整快照。
5. HTTP 响应等待上述操作完成后返回。

### 11.8 自然播放结束

1. 播放器只报告 `track_ended(current_item_id)`，不自行查询或删除下一项。
2. 状态机验证事件仍对应当前歌曲，拒绝迟到事件。
3. 当前队列项标记为 `played`，写入播放序号和历史。
4. 选择器按照播放模式返回下一项。
5. 释放旧缓存租约，获取新缓存租约。
6. revision 加一并发布完整快照。
7. 新项目未准备好时等待其高优先级准备，不擅自越过正常队列顺序。

### 11.9 手动上一首/下一首

1. 命令进入状态机。
2. 依据当前 mode、历史、进度和命令原因运行纯选择函数。
3. 播放器停止当前文件读取并切换文件。
4. 原来为 paused 时继续 paused；原来为 playing 时继续 playing。
5. revision 加一，HTTP 返回应用后的新状态。

### 11.10 编辑活动队列

- 普通成员删除未播放项：仅允许删除 `requested_by_user_id` 等于自己的临时条目；标记为 removed，取消其独占预取，保持当前歌曲。
- 普通成员删除当前项：仅在当前歌曲由自己点播时允许，通过统一切歌流程释放资源并选择下一项。
- 管理员及更高权限删除：可以删除任意临时条目，包括当前项。
- 管理员立即播放：执行 `play_now`，目标歌曲立即成为当前项；点歌队列同时原子重排为“被中断歌曲 → 目标歌曲 → 原后续歌曲”，房间歌单和个人歌单保持原顺序。
- 移动项目：在事务中重排，只影响尚未播放部分；历史顺序不改。
- 一键清空临时歌单：仅管理员及更高权限可执行；临时歌单为激活来源时停止播放，释放其租约并清理当前项、待播条目和受限历史；不删除已保存歌单和公共缓存。
- 清空已保存歌单快照：只清理本轮活动快照，不删除作为来源的个人歌单或房间歌单。
- 失败项：保留可见错误和重试入口，不让状态机无限重试。

### 11.11 客户端重新连接

1. SSE 断线重连后，客户端调用 `GET /state` 获取完整快照。
2. 客户端用 revision 替换本地状态。
3. 进度事件只有在 room、revision 和 current item 都匹配时才应用。
4. 客户端没有加入 LiveKit 语音时仍可看状态和控制，但不接收音乐音轨。

### 11.12 服务重启

第一版采用保守恢复：

- 保留 Track、Playlist、PlaylistItem、房间临时歌单、活动快照、受限历史、激活来源和播放模式。
- 不删除有效缓存文件。
- 不自动连接音乐机器人，不自动恢复出声。
- 把实时播放状态安全置为 `stopped`，position 置零。
- 可以保留 current item，使用户点击播放后从该曲开头开始；如果该项已被删除则选择下一有效项。
- 清理残留临时文件和过期任务状态。
- 缓存文件缺失时把索引修正为 missing，后续按需重新准备。

这样既不会因为服务重启丢失歌单，又不会在无人确认时突然恢复音乐。

### 11.13 语音频道无人时自动清理

“无人”只统计真实、可见的语音成员，不把 `__musicbox__` 音乐机器人、屏幕音频辅助连接、隐藏发布者或仅存在于过期缓存中的成员算作在线用户。

1. 最后一名真实语音成员离开后，房间状态机记录 `voice_empty_since` 并启动可取消的宽限计时，建议默认 10 分钟。
2. 宽限期内任意真实成员重新加入时取消本轮清理，不能让迟到定时器清空已经重新使用的房间。
3. 宽限期到期时，以带 generation/token 的 `temporary_playlist_expired` 事件重新投递给房间状态机。
4. 状态机再次确认语音频道仍无人，然后停止音乐机器人、释放缓存租约、清空临时歌单的当前项、待播项和历史，并丢弃本轮已保存歌单活动快照。
5. 已保存的房间歌单和个人歌单不受影响；下次有人使用音乐盒时默认激活一个空临时歌单，模式恢复为 `sequential`。
6. revision 增长并广播清理后的状态；若房间已经没有 SSE 订阅者，仍需保存恢复点和记录结构化日志。

计时不能用无法取消的裸 goroutine 直接修改房间字段。它只能投递带代次的事件，由单一写入者复核占用状态，避免成员刚重新加入就被旧计时器误清空。

### 13.4 分页与批量操作

- 歌单列表和歌单项必须分页。
- 批量添加歌单到房间使用一个幂等请求和一个数据库事务。
- 房间歌单管理中，每行原有的单歌单“删除”按钮替换为“克隆”；删除仍通过顶部勾选后的批量删除入口完成，不提供批量克隆。克隆把该房间歌单复制到当前用户的“我的歌单”，目标名称使用当前用户的房间备注名（没有备注时回退房间名）与原歌单名组成“房间名 · 歌单名”，中点前后固定保留一个空格，重复名称沿用个人歌单的自动编号规则。服务端必须锁定用户容量并在一个事务内复制歌单与全部歌曲，个人歌单已达 50 个时返回 `playlist_limit_reached`，不能留下空歌单或部分歌曲。客户端应在确认窗口关闭且页面状态稳定后显示全局浮窗：成功时显示“已克隆到我的歌单 - 目标歌单名”，容量已满时明确显示 50 个上限。
- “我的歌单”和“房间设置 - 歌单”的歌单级批量“分享”统一改为“合并”。用户按点击顺序选择至少两个歌单并输入目标名称；客户端必须在执行前再次确认，来源歌曲总数超过 500 时还要明确提示可能无法全部合并，并只在用户选择“继续合并”后提交。歌曲按所选歌单顺序及各歌单内部顺序处理，以 `source + external_track_id` 表示的具体链接去重，不能仅按显示名称去重。
- 合并是消费来源的单一数据库事务：去重后的前 500 首写入新歌单；已经完整处理的来源歌单删除；达到 500 首时，只删除当前来源歌单中已经处理的前缀，未处理的后缀和后续来源歌单保持不变。删除来源、裁剪部分来源、创建目标和写入目标歌曲中的任一步失败都必须整体回滚。目标歌单在释放已完整处理来源的名额后创建，因此已有 50 个歌单时仍可合并；服务端响应应返回原始歌曲数、唯一链接数、去重数、写入数、未写入数、删除/保留来源数及是否截断，客户端据此显示完成或未全部合并的浮窗提示。
- “我的歌单”和“房间设置 - 歌单”的歌曲级批量“分享”统一改为“添加到歌单”。用户按点击顺序选择歌曲、选择同一作用域内的另一个目标歌单，并在二次确认后提交；添加只复制歌曲，永远不删除或改动源歌单。服务端必须在单一数据库事务内按选择顺序处理，以 `source + external_track_id` 的具体链接去重，并同时锁定源、目标及用户/房间歌单命名空间；目标中已存在的链接跳过，剩余容量不足时只追加前缀至 500 首。客户端在提交前根据摘要提示目标剩余容量，服务端响应仍返回所选数、唯一链接数、所选内部重复数、目标已存在数、新增数、因上限未添加数和截断状态，以便显示准确浮窗；房间歌单接口必须继续要求管理员及以上权限。
- 响应不必返回全部 500 个歌单项；返回摘要、revision 和第一页，后续按页获取。
- 房间完整快照在队列较大时也应支持摘要与分页演进，但第一阶段可在 200 首上限内继续返回完整活动队列。

## 15. 权限和安全

临时歌单权限矩阵：

| 操作 | 普通成员 | 房间管理员及更高权限 |
|---|---:|---:|
| 搜索和点歌 | 允许 | 允许 |
| 切换到有权访问的歌单 | 允许 | 允许 |
| 删除自己点的临时条目 | 允许 | 允许 |
| 删除他人点的临时条目 | 禁止 | 允许 |
| 播放/暂停、上一首/下一首 | 禁止 | 允许 |
| 切换临时歌单播放模式 | 禁止 | 允许 |
| 重排临时歌单 | 禁止 | 允许 |
| 立即播放某个临时条目 | 禁止 | 允许 |
| 一键清空临时歌单 | 禁止 | 允许 |

- “普通成员只能点歌、切换歌单、删除自己点的歌”必须由服务端逐项强制执行，不能依赖客户端隐藏控件。

已保存歌单控制矩阵：

| 当前激活歌单 | 普通成员 | 管理员及更高权限 |
|---|---|---|
| 自己的个人歌单 | 完整播放控制、重排、切换全部播放模式 | 歌单属于自己时同左 |
| 房间歌单 | 完整播放控制、重排、切换全部播放模式 | 完整播放控制、重排、切换全部播放模式 |
| 其他成员的个人歌单 | 只能切换/查看，不能播放控制、重排或切换模式 | 仅当歌单所有者的当前房间角色严格低于操作者时，拥有完整播放控制、重排和模式切换 |

- “完整播放控制”包括播放、暂停、上一首、下一首和停止，但不包含临时歌单专属的 `play_now` 或清空临时歌单。
- 个人歌单的持久重排必须同时验证“本人”或“管理员高于所有者”的关系；只控制活动快照时也必须执行相同角色比较，不能留下绕过入口。
- 角色高低使用服务端当前房间成员角色计算，例如普通成员 `<` 管理员 `<` 创建者/更高管理角色；超级用户按现有全局权限规则参与比较。
- 同级管理员之间不能相互越级控制个人歌单，低权限用户也不能通过转发 command ID 或复用旧 revision 绕过检查。
- 切换歌单只表示选择激活来源，不自动授予控制能力。服务端在每次命令执行时重新校验，客户端 capabilities 只用于显示。
- 个人歌单的重命名、简介、共享范围和整单删除只有所有者可操作；条目重排按上表允许管理员对低权限所有者越级控制。
- 房间歌单允许所有房间成员重排；重命名、简介、增删条目和整单删除默认仍由房间管理员管理，其他持久编辑能力由独立权限决定。
- 播放个人歌单到房间时，调用者必须同时拥有歌单访问权和房间成员权限。
- 已载入房间的个人歌单使用独立活动快照；歌单所有者离开房间不会让当前歌曲突然中断，也不会让其他成员获得原个人歌单的编辑权限。
- 所有队列操作按 `(room_id, item_id)` 查询和更新。
- 所有歌单条目操作按 `(owner/scope, playlist_id, item_id)` 查询和更新。
- 不向客户端暴露服务端文件路径、解析后的临时音源 URL、LiveKit token 或第三方鉴权信息。
- 对歌单名、简介、歌名、歌手、音源 ID 和批量项目数量设置长度限制。
- 下载和转码继续使用受控超时、并发上限、临时文件和目标路径清理。

## 16. 缓存与预取策略

### 16.1 优先级

准备任务分为：

1. 当前待播放项：最高优先级。
2. 后续第 1、2 首：普通预取。
3. 其他队列项：不主动下载，除非容量和策略明确允许。

随机模式应根据当前洗牌袋预取，而不是按显示 sort order 预取。临时歌单不进入随机模式，始终按稳定待播顺序预取。

### 16.2 并发去重

相同 cache key 在整个服务进程中只能有一个准备任务。其他房间等待同一个结果。任务完成后分别向等待它的房间状态机发送事件。

### 16.3 清理

缓存清理器按配置周期运行：

- 跳过存在有效租约的文件。
- 优先清理校验失败、长期失败和最久未使用的缓存。
- 达到软上限开始清理，降到目标水位后停止。
- 达到硬上限时拒绝低优先级预取，但当前歌曲仍可尝试准备或返回明确错误。
- 数据库索引存在但文件缺失时修正为 missing。
- 文件存在但无索引时视为孤儿，在安全期后清理。

对象存储只作为未来多实例共享冷缓存选项。即使启用对象存储，本地磁盘仍作为播放热缓存，避免播放循环直接依赖远端对象读取。

## 17. 客户端 UI

### 17.1 基础控制

控制顺序建议为：

```text
上一首 | 播放/暂停 | 下一首 | 播放模式
```

- 播放模式按钮使用已有立体按钮和已有弹出菜单样式。
- 临时歌单的模式菜单只显示“顺序播放”和“单曲循环”；已保存歌单显示全部四种模式。
- 当前为临时歌单且用户是普通成员时，不显示或禁用播放/暂停、上一首、下一首和模式控制，只保留点歌、切换歌单和删除本人条目的入口。
- 当前为自己的个人歌单或房间歌单时，普通成员显示完整播放控制、重排和全部模式；当前为其他成员个人歌单时，仅在服务端 capabilities 允许的管理员界面显示这些控制。
- 按钮状态由 `lib/src/app` 的纯 display/helper 计算。
- 控制请求进行中只禁用会冲突的按钮，不冻结整个音乐盒。
- 收到更高 revision 后解除 pending 状态。
- 窄屏时允许缩为图标，但必须保留 tooltip、语义标签和触屏可用热区。

### 17.2 歌单入口

后续音乐盒主体可以分为：

- 搜索。
- 点歌队列（协议内部仍为 `temporary`）。
- 房间歌单。
- 我的歌单。

队列栏应直接显示当前激活来源的具体名称，并允许在点歌队列、房间歌单和有权访问的个人歌单之间切换。音乐盒标题旁不再重复显示“当前：xxx”，也不展示转码缓存占用。成员点歌后，即使当前正在播放已保存歌单，也要更新点歌队列的数量提示，避免用户误以为点歌丢失。

队列标题右侧的加号负责展开“搜索添加 / 房间歌单 / 我的歌单”。加号左侧固定一个上下文
按钮：当前来源不是点歌队列时用于切回点歌队列，不再在歌曲列表顶部重复放置返回按钮；
当前来源是点歌队列时用于清空，并在队列为空时禁用。清空必须使用已有确认对话框样式，
携带确认前快照的 `expected_revision`，服务端只清空临时队列；如果它是当前来源则同时
停止播放，绝不删除任何已保存歌单或其独立活动快照。加号展开来源选择器时隐藏该上下文
按钮，让选择器获得完整可用宽度；收起选择器后按当前来源恢复对应按钮。
从点歌队列删除条目成功后使用应用已有的浮动弹窗式提示明确显示已删除的歌名；失败时继续显示服务端错误映射。提示只在服务端成功返回权威快照后出现，不先于真实删除状态。

房间歌单或我的歌单为空时，空状态除图标和说明外还显示“新建第一个歌单”。个人入口由 Home 导航统一打开“设置 → 我的歌单”；房间入口仅在当前用户具备房间管理权限时显示，并统一打开“房间设置 → 歌单”。音乐盒组件本身不得私自创建新的路由或对话框。这样 Android 独立页面与 Windows/macOS 嵌入页面继续复用各自已有的返回栈和关闭行为；普通设置入口仍默认打开用户资料，普通房间设置入口仍默认打开房间信息。

点歌队列的紧凑行统一使用音乐图标，只保留歌名、歌手与必要的下载状态，不再显示时长、“· 来源”、点歌人头像或“由 xxx 点歌”。时长和来源仍在歌曲名片内完整展示。点击歌曲行使用与用户/房间名片相同的已有悬停/点击名片交互，名片展示名称、时长、歌手和来源：点歌队列条目显示右对齐且彼此紧邻的点歌人头像与名称，点歌人头像继续嵌套已有用户名片，可解析最新用户资料、当前房间身份、共同房间并进入房间；当前操作者权限足够时，名片复用房间成员已有的“管理成员”入口。点歌人名称本身使用普通文本，不重复提供选择菜单。已保存歌单快照条目的“歌单”字段只显示“歌单图标＋完整歌单名称”，不再重复拼接创建人或房间前缀；该身份组继续使用已有悬停/点击机制打开对应歌单名片，创建人或房间归属改在歌单名片中完整展示。点歌人及个人歌单所有者的预设头像使用全局昵称或用户名生成文字，不能使用房间专属名称；展示名仍可使用房间名。名片提供服务端允许的“优先播放”和“添加到歌单”，删除、优先播放和歌单写入均由服务端重新校验，客户端显示不能成为授权依据。

搜索结果和音乐盒内打开的已保存歌单歌曲复用同一套目录歌曲行与名片交互。目录行只显示音乐图标、完整歌曲名和完整歌手名，不在副标题重复来源；右侧加号直接加入点歌队列，点击行本身只打开歌曲名片。目录歌曲名片隐藏尚不存在的点歌人/来源歌单归属，主操作文案统一为紧凑的“点歌队列”，并继续提供“添加到歌单”；服务端接口仍按目录项的来源与 track ID 执行，不伪造队列项。设置和房间设置里的歌单管理页使用相同的歌曲详情样式，但将“优先播放”替换为本地“试听/取消试听”，不显示或触发房间播放动作。已保存歌单项的时长应传入名片，搜索结果在上游未提供时显示“未知”。

哔哩哔音源的歌曲名片在点歌人/来源歌单归属之后增加“详情”行，显示服务端保存的 BV 号。目录项尚无归属行时，“详情”仍作为基础详情的末行显示。客户端可从包含 BV 号的 track ID 中提取展示，不修改实际传给服务端的 track ID。

歌曲名片的标题、时长、歌手、来源、歌单归属和 BV 详情复用用户/房间名片的只读可选择文本交互。Windows 与 macOS 右键时可复制当前选区，没有选区时默认选中当前字段；Android 使用同一组长按、双击、选择手柄和菜单行为。点歌人名称按上一段保持普通文本，交互入口统一放在其头像用户名片上。文本菜单、Android 选择手柄或嵌套用户名片活动期间必须保持歌曲名片打开，不得被外部点击判定误关闭。

嵌套用户名片和房间名片在可用宽度不足时同样完整展示，不使用省略号丢失用户名、房间名、共同房间名或创建者名称。名片头部长名称可以完整换行；共同房间和成员等紧凑身份行则始终优先把“头像＋用户名”或“房间图标＋房间名”保留为同一个单行身份组。可用宽度必须取当前名片完成宽度限制、内边距和字段分栏后的实际内容宽度，不能使用屏幕宽度或固定桌面名片宽度；身份组确实放不下时切换为小头像并等比缩小完整名称，身份、状态或角色等后续信息空间不足时移到下一行。

“添加到歌单 → 选择歌单”只显示歌单完整名称，不再把“房间 ·”或“我的 ·”接到名称前。作用域继续由现有房间/用户图标表达；目标行复用普通歌单摘要的中性卡片样式与最小高度，右侧只保留独立加号按钮，不显示播放、数量或导航箭头。超长歌单名按歌曲名的规则换行并小幅缩小字号，按钮高度随完整文本增长，不使用省略号。多个选项超出名片可用高度时只滚动选项列表。

已保存的房间歌单和个人歌单统一复用歌单名片。歌单摘要、当前已保存歌单标题以及“添加到歌单 → 选择歌单”的目标主体均可通过已有悬停/点击机制打开名片；进入歌单后的标题仅静态显示“歌单图标＋完整歌单名”，不打开名片，返回与播放按钮保持独立热区。普通歌单摘要行不显示“XX 首”，把空间留给完整名称，右侧播放按钮之后使用保持小图标但扩大到整行高度的导航热区。选择目标行右侧保留独立添加按钮，点击添加不能同时误触发名片。名片显示完整歌单名称、歌曲数量、创建日期，以及“房间图标＋房间名”或“用户头像＋用户名”的归属身份；字段名和字段值均使用与歌曲名片详情相同的紧凑字号。创建人在当前房间有专用名时必须优先显示专用名，头像仍按全局身份生成。所有字段值共用右对齐边界，头像与名称作为一个靠右单行整体，宽度不足时整体等比缩小，不能把名称拆成多行。身份整体继续嵌套已有房间名片或用户名片，打开子名片时父歌单名片保持可见。底部固定提供“播放全部”和“查看歌单”，复用现有自适应按钮与服务端权威控制流程。从当前已保存歌单标题打开时，不再在标题下方另放状态标签，而是将“播放全部”替换为不可重复触发的禁用态“正在播放”；普通歌单列表仍显示可用的“播放全部”。临时点歌队列不是可复用歌单，不提供歌单名片，也不显示创建日期。

当当前来源是其他成员的个人歌单时，“查看歌单”打开独立只读窗口，而不是尝试访问对方的私有原歌单。窗口固定读取本轮活动播放快照，完整列出全部歌曲；歌曲行复用已保存歌单的完整标题/歌手布局和歌曲名片，支持本地试听及添加到自己已有歌单。底部提供“克隆到我的歌单”和“完成”。克隆请求必须携带当前 `playlist_id` 与不可变 `snapshot_id`，服务端确认活动来源仍匹配后，在同一数据库事务内校验个人歌单上限和 500 首歌曲上限、创建歌单并按快照顺序写入全部歌曲；任何一步失败都不得留下空歌单或部分歌曲。首次克隆名称为“房间内专用名的歌单 · 原歌单名”，重复名称自动追加序号且总长度不超过 64 字符。当前来源已切换、快照标识过期、来源是自己的歌单或歌单已满时返回稳定错误码，客户端保留查看窗口并显示已有浮动提示。

歌单标题和歌曲名片“歌单”字段中的歌单图标都按完整多行名称的高度垂直居中，不能固定贴第一行。切换到已保存歌单时，活动来源快照同时固化并发布原歌单的真实创建时间，使其他成员无需访问私有原歌单也能显示创建日期；只对旧服务端快照或真实缺失的数据回退显示“未知”。临时点歌队列仍不显示创建日期。

查看其他成员的活动歌单时，歌曲行和“我的歌单”歌曲行复用同一表面、内边距与字体布局，普通两行内容高度一致，长标题仍按完整内容自适应增高。

音乐盒中的歌曲标题不得用省略号丢失内容。歌曲名片先按两行测量，超过两行时根据实际
行数逐级缩小字体，并允许扩展到三行、四行或更多行；队列、搜索结果、已保存歌单歌曲行
以及歌单摘要名称也应按完整内容增加自身高度。该自适应只作用于音乐盒组件，不改变应用内
其他固定高度列表，避免引入跨页面布局回归。

条目处于等待下载或下载中时，加载动画替换行首音乐图标并保持相同占位尺寸，不在歌曲
来源文字前额外插入动画，避免下载状态变化导致标题与副标题水平跳动。

歌单列表分页加载，单个已保存歌单进入后显示项目列表、重排、删除、切换播放和追加到临时歌单等操作。临时歌单只提供当前房间所需的队列编辑、清空和受限历史展示。不能因为打开 500 首歌单而一次构建或下载全部音频。

### 17.3 进度显示

- 播放控制和歌曲切换只认服务端状态。
- 精简进度事件只更新进度，不覆盖队列。
- 收到不匹配当前歌曲或旧 revision 的进度事件时丢弃。
- SSE 重连、App 从后台恢复或切换房间后重新获取完整状态。

## 18. 可观测性

服务端至少记录或统计：

- 活跃音乐房间数和音乐机器人连接数。
- 控制命令排队时间、处理时间、超时和失败数。
- 当前队列长度、歌单载入数量。
- 搜索耗时与上游错误率。
- 缓存命中率、缓存大小、清理数量。
- 下载/转码耗时、失败率和 worker 使用率。
- LiveKit 发布失败、断开和重连次数。
- 优先播放切换耗时、失败数，以及优先播放期间意外发生的音乐机器人重连次数（正常应为 0）。
- 临时歌单点歌、按所有者删除、管理员删除、立即播放和一键清空次数。
- 已保存歌单控制允许/拒绝次数，并区分本人、房间歌单、低权限所有者、同级和高权限所有者。
- 语音频道空置计时启动、取消、到期清理和代次不匹配丢弃次数。
- SSE 完整快照与进度事件的数量、平均 payload 大小。
- revision 冲突和客户端旧事件丢弃数量。

日志关联字段建议包含 `room_id`、`command_id`、`queue_item_id`、`cache_key` 的不可敏感部分和 `revision`。不得记录临时音源 URL、访问 token 或第三方 cookie。

## 19. 测试方案

### 19.1 服务端纯逻辑测试

`selector.go` 应使用表驱动测试覆盖：

- 空队列、单曲、两首、多首。
- 四种播放模式。
- 临时歌单只接受 `sequential` 和 `repeat_one`。
- 已保存房间歌单和个人歌单接受全部模式。
- 自然结束与手动 next。
- 单曲循环自然结束重复、手动 next 前进。
- 3 秒阈值前后的 previous。
- 临时歌单历史窗口淘汰后 previous 不越界。
- 暂停时切歌保持暂停。
- 随机一轮不重复。
- 随机跨轮避免首尾立即重复。
- 随机模式新增、删除歌曲。
- 当前歌曲失败或被删除。

### 19.2 服务端状态机测试

- 命令按顺序处理且不会静默丢失。
- HTTP 等待应用后的 revision。
- 迟到的 `track_ended` 不会跳过新歌曲。
- 多人同时点歌顺序唯一且稳定。
- 多人点歌始终加入同一房间临时歌单。
- 临时条目点歌人取自认证用户，不能由请求体伪造。
- 普通成员只能删除自己的临时条目。
- 普通成员对临时歌单的播放、切歌、模式、重排、立即播放和清空命令均被拒绝。
- 普通成员可以完整控制自己的个人歌单和房间歌单。
- 普通成员切换到他人个人歌单后不能播放控制、重排或切换模式。
- 管理员只能越级控制角色严格低于自己的用户歌单，同级和更高角色均被拒绝。
- 角色在命令排队期间变化时，执行阶段按新角色拒绝已经失效的权限。
- 管理员可以删除任意临时条目并一键清空。
- `play_now` 把被中断歌曲压入历史，使其成为上一首。
- 从已保存歌单执行 `play_now` 会切到临时歌单，且上一首仍能返回被中断歌曲。
- 暂停状态执行 `play_now` 后目标歌曲实际进入播放状态。
- `play_now` 目标等于当前歌曲时只从头播放且不重复写历史。
- 播放中和暂停中执行 `play_now` 均复用现有 LiveKit participant 与 Opus track，不重新
  获取 token、不重连，也不等待旧 identity 清理。
- `play_now` 成功响应之前，目标已成为当前歌曲、位置为 0；无播放器时建连失败不会
  写入半成功状态。
- 歌曲名片持有旧 revision 时，客户端仍只发送目标与幂等 command ID；服务端按执行时
  的活动队列和 ready 状态决定是否接受。
- 播放已保存歌单时点歌不会修改当前快照或原歌单。
- 切回临时歌单能恢复待播内容和受限历史。
- 切换到不支持当前模式的来源会原子回退为顺序播放。
- 删除当前项只切换一次。
- 重复 command ID 只应用一次。
- revision 冲突不会覆盖新状态。
- 播放器断开、重连和关闭时释放资源。
- 服务重启保留歌单/队列但不自动出声。
- 空语音频道宽限期内重新加入会取消清理。
- 迟到的空房间计时事件不会清理已经重新使用的房间。
- 空置到期只清理临时歌单和活动快照，不删除已保存歌单。

### 19.3 缓存测试

- 相同歌曲并发请求只启动一次转码。
- 不同房间可以共享 ready 缓存。
- 正在播放的缓存不会被清理。
- 预取取消不影响其他等待者。
- 临时文件失败后不会被误认为 ready。
- 缓存索引与磁盘不一致可以自愈。
- LRU 在软/硬上限下行为正确。

- 最大条目限制。
- 重排与唯一顺序。

- 重复项。

- 跨房间和跨用户权限隔离。

### 19.6 客户端 widget 测试

放在 `test/widget/home`：

- pending、失败、空歌单和长歌名单。
- 上一首/下一首/模式按钮正确调用 controller。
- 临时歌单不显示列表循环和随机播放。
- 每个临时条目显示点歌人，普通成员只看到自己条目的删除入口。
- 普通成员使用临时歌单时不显示无权限的播放、切歌、模式和重排入口。
- 自己的个人歌单与房间歌单显示完整控制；他人个人歌单根据最新 capabilities 隐藏或禁用控制。
- 管理员操作菜单提供立即播放，清空临时歌单需要危险操作确认。

  按钮切回点歌队列，列表内不再重复显示返回按钮。

## 21. 回归风险

主要风险和对应防护：

| 风险 | 防护 |
|---|---|
| 新旧客户端事件契约不同 | 先加字段和事件，保留旧完整心跳，分阶段切换 |
| 状态机阻塞音频线程 | packet 写入与数据库/SSE 分离，完成事件回投状态机 |
| 缓存清理删除播放中文件 | 租约、临时文件、原子重命名和清理测试 |
| 随机/上一首在队列编辑后错乱 | 显式历史和洗牌袋，不从 sort order 猜历史 |
| 切换歌单导致临时点歌丢失 | 临时歌单独立保存，切换只替换活动快照 |
| 临时歌单误启用随机或列表循环 | 服务端能力矩阵校验，客户端只作提前限制 |
| 客户端伪造点歌人或越权删歌 | 点歌人取认证会话，所有删除/清空/立即播放均由服务端复核角色 |
| 旧角色缓存导致越级控制他人歌单 | 每条命令执行时读取当前角色，角色变化提升 revision 并刷新 capabilities |
| 同级管理员互相覆盖个人歌单 | 只允许严格高于所有者的角色越级，控制权不等于所有权 |
| 立即播放破坏上一首历史 | 在同一状态机事务中先压入当前项，再提升目标项 |
| 迟到空房间计时器误清新队列 | 可取消计时、代次 token 和状态机内二次占用检查 |
| 并发点歌顺序重复 | 单房间串行分配或数据库事务与唯一约束 |
| 服务重启突然自动播放 | 重启统一进入 stopped，不自动连接机器人 |
| 大歌单扩大 SSE 和 widget 开销 | 队列上限、分页、精简进度事件和惰性列表 |
| Android 修改影响桌面 | 业务规则共享，只有响应式 UI 分支做平台差异测试 |

## 23. 最终原则

后续实现应始终遵守以下边界：

1. 服务端是播放顺序和播放状态的唯一权威。
2. 客户端只做控制、展示和本地监听音量，不自行播放音源。
3. 临时歌单是房间默认工作队列；已保存歌单是持久模板，播放时使用独立活动快照。
4. 音频是可重建缓存，不能与歌单生命周期绑定。
5. 所有房间播放变更经过同一个串行状态机。
6. 所有快照和控制结果带 revision，拒绝旧状态覆盖。
7. 播放 packet 路径不执行数据库、HTTP、SSE 或缓存清理。
8. 大歌单必须分页、按需预取，不能全量下载或逐秒全量广播。
9. 新接口采用向后兼容的增量迁移，不一次破坏现有客户端。
10. 每个阶段先完成状态机和边界测试，再接 UI。
11. 临时歌单点歌人和权限以服务端认证身份为准，客户端显示不能成为授权依据。
12. 空房间清理由可取消、带代次且经过状态机复核的事件执行，不能由定时器直接改状态。
13. 切换到歌单不等于取得控制权；个人所有权、房间歌单能力和基于角色高低的越级控制必须分别校验。
